## Description
**What**: Extracts the "is this command a `git commit`?" test out of `commit_title_length_guard.sh`, `commit_body_wrap.sh` and `commit_secret_guard.sh` into one shared matcher, and fixes the four invocation shapes all three of them silently missed.

**Why**: The three guards each carried their own copy of the same anchored regex:

```
^[[:space:]]*(rtk[[:space:]]+)?git[[:space:]]+commit([[:space:]]|$)
```

It recognised exactly two spellings. Every other spelling made all three guards exit 0 without looking at anything — a guard that no-ops is indistinguishable from a guard that passed. Measured in this repo: a 78-character commit title reached gitlint and was rejected *there*, having sailed past the title guard that exists to catch exactly that. The commit had been chained after `git add`.

**How**: `ai_clients/claude/hooks/lib/commit_command_matcher.sh`, sitting alongside the existing `lib/review_thread_gate.sh`, exposes `command_has_git_commit`. All three guards source it. Detection is a token walk rather than one regex — which is what makes the path- and flag-bearing shapes expressible at all.

**Fixed**:
- Issue #324: four invocation shapes that made all three guards no-op.

| shape | before | after |
|---|---|---|
| `git commit -m x` | MATCH | MATCH |
| `rtk git commit -m x` | MATCH | MATCH |
| `rtk proxy git commit -m x` | **MISS** | MATCH |
| `git add -A && git commit -m x` | **MISS** | MATCH |
| `/usr/bin/git commit -m x` | **MISS** | MATCH |
| `git -C /some/path commit -m x` | **MISS** | MATCH |
| `/usr/bin/git -C "$dir" commit -F "$msg"` | **MISS** | MATCH |

The last three were found *after* the first fix, by probing the matcher against the command the first commit on this branch was written with. `/usr/bin/git` and `git -C <dir>` are not exotic spellings here — the global `CLAUDE.md` and the `dev-loop` skill mandate the first where the rtk proxy must be bypassed, and both discourage `cd <dir> &&` in favour of the second. Their composition is the house style for commits, so the guards were off for the commits most worth guarding.

**Preserved**: the per-segment anchor. The binary must be the first token of its segment, so a mere *mention* of "git commit" inside an argument still never matches. Losing that would turn the guards into false-positive machines, which #324 is explicit about.

## Additional Notes
**Dependencies**:
- None. Independent of #322 and #323.

**Follow-up**:
- The chain split (`&&`, `||`, `;`, `|`) is a regex over the raw string, not a shell parse — the same heuristic every guard in this repo already uses. A chain operator appearing literally inside a quoted argument can still confuse it. Marked with a `ponytail:` comment naming the ceiling and the upgrade path (real argv/AST parsing); not worth building until it produces a real miss.
- The guards take effect on this machine only after `bash ai_clients/claude/main.sh hooks` redeploys `~/.claude/hooks/`. Until then the old two-shape matcher stays live — the deployed-vs-source split this repo has been bitten by before.

**Reviewer Focus**:
- `_segment_invokes_commit` in the matcher, specifically the `_GIT_VALUE_FLAGS` skip. Flags whose value is a separate token (`-C`, `-c`, `--git-dir`, …) must have that value skipped, or `git -C commit status` reads as a commit. The `--flag=value` spellings carry their value in one token and need no entry.
